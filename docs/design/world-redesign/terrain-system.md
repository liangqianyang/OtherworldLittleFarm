# 居住区地形改造系统设计（Terrain System）

> 文档状态：v1（2026-11-16）。归属 docs/design/world-redesign/。
> 任务来源：用户拍板「我希望我的居住区域是可以调整地形的，比如有河流，有台阶，有地窖等等」——地形改造是本作核心特色模块。
> 上游决策对齐：game-design-draft.md §5.3（首版平面+遮挡）、design-improvement-proposal.md §3.1（高度系统降级）与 §3.2（装扮预布置）、pitfalls.md（程序化节点 layer / cc 枚举导入 / Sprite sizeMode）。
> 所有数值均为起点值，以灰盒原型与真机实测为准。

---

## 0. 定位与边界（先划红线）

**本系统 = "假高度 + 可编辑地皮"，不是真 3D 高度系统。**

建议书 §3.1 已拍板：探险图首版"平面+遮挡"，真实高台/楼梯的全套高度判定（射线、近战可达、寻路、跨层陷阱）被砍。居住区地形改造**不恢复那套系统**，而是采用：

- 每格一个 `heightLevel` 整数（0-3），**只影响"能不能走过去"和"立面贴图"**，不产生跨层弹道、跨层寻路、跨层视野判定；
- 立面是贴在高低边界上的**装饰 Sprite**，进入 y-sort 队列，复用 §5.3 的遮挡可读性规范（脚底阴影=可行走真值、遮挡淡出 40-50%）。

这样居住区"有台阶、有河、有高台"的体验成立，而探险图保持平面+遮挡不返工。若未来探险图 spike 通过要恢复真高度，再评估两套系统的合并（见 §10）。

**本系统的范围（MVP）**：
- 一张"家园大地图"（替代现有 3×3 农场切片的正式形态），含住宅庭院可编辑区；
- 可编辑：耕地、石板路、木平台、台阶、桥、地窖入口；
- 河流为**地图预设不可挖改**（挖池塘/改河道延后，见 §10）；
- 地窖为独立室内场景（方案 B，见 §5）。

## 2. Tile 类型体系

### 2.1 地形 ID 表（地面层，每格一个 terrainId）

| terrainId | 常量名 | 名称 | 混合方式 | 可走 | 高度 | 编辑工具 | 备注 |
|---|---|---|---|---|---|---|---|
| 0 | VOID | 空白/虚空 | 无 | ✗ | - | - | 地图外圈/树丛底格，纯黑或树影 |
| 1 | GRASS | 草地 | 单 tile | ✓ | 任意 | -（默认底色） | 不需要变体，所有混合压力在"特征地形"边缘 |
| 2 | DIRT | 泥地 | 单 tile | ✓ | 任意 | 铲子副产品 | 踩实土路感，可加 2-3 个随机点缀变体 |
| 3 | TILLED | 耕地 | 16 变体 | ✓ | 任意 | 锄头（草→耕） | 复用 plot_soil/plot_soil_wet 素材；作物数据仍在 farm.plots（§7.4） |
| 4 | WATER | 水域 | 16 变体+3 帧动画 | ✗（桥除外） | 固定 0 | **MVP 不可编辑** | 河岸变体见 §3.1 |
| 5 | STONE_PATH | 石板路 | 16 变体 | ✓ | 任意 | 铺装器·石板 | |
| 6 | WOOD_DECK | 木平台 | 16 变体 | ✓ | 任意 | 铺装器·木板 | 户外露台/栈道 |
| 7 | STAIRS | 台阶 | 2 方向变体 | ✓（过渡格） | 任意（连 Δ≤1） | 台阶锹 | 见 §4 |
| 8 | BRIDGE | 桥 | 2 方向变体 | ✓ | =两岸高度 | 造桥锤 / 铲子拆除 | 见 §3.3 |
| 9 | INDOOR_FLOOR | 室内地板 | 16 变体 | ✓ | 0 | 室内装修（二期） | 室内场景复用同一渲染器与编号 |
| 10-15 | — | 预留 | — | — | — | — | 花坛/地毯/榻榻米等季节与室内变体 |

- 编号 4 bit（0-15）+ 高度 3 bit（0-7），打包进 1 字节：`byte = (terrainId << 3) | heightLevel`，最大 `(15<<3)|7 = 127` ✓。
- **地窖入口不是地形**，是庭院里的 1×1 可交互物件（y-sort Sprite），数据存 `terrain.cellars`（§5、§7）。

### 2.2 图集组织

沿用 SpriteLib 路径约定（`tiles/<name>/spriteFrame`，pitfall #20/#21 的 meta 约定照旧：minfilter=nearest、trimType=false、赋图前 sizeMode=CUSTOM）：

```
assets/textures/tiles/
  ground_grass.png        32×32   单 tile
  ground_dirt.png         32×32   单 tile（+2 个点缀变体 dirt_a/dirt_b 可选）
  tilled_sheet.png        128×128 4×4 = 16 变体（idx=行内序号 0-15）
  water_sheet.png         160×128 5×4 = 16 变体 + 3 帧中心动画帧（idx 16/17/18）
  stone_path_sheet.png    128×128 16 变体
  wood_deck_sheet.png     128×128 16 变体
  indoor_floor_sheet.png  128×128 16 变体
  stairs_ns.png / stairs_ew.png   台阶两方向
  bridge_ns.png / bridge_ew.png   桥两方向
  facade_stone_16.png / facade_stone_24.png / facade_cliff_16/24.png   立面（含崖顶描边）
```

- 单张 sheet ≤128×128，全部图集合并后约 90-110 个 tile，**远低于建议书 §8"tile 60-100 张、整包素材 ≤6MB"预算**（tiles 图集 pngquant 后估计 ≤300KB）。
- sheet 内 tile 索引规则统一：`idx = (row*4 + col)`，运行时 `SpriteFrame` 引用按表驱动，不散落硬编码。

### 2.3 轻量 auto-tile：**16 变体直接映射**（推荐），对比 47 / 13 / 9-slice

| 方案 | tile 数/地形 | 判定 | 问题 |
|---|---|---|---|
| 47 变体 blob | 47 | 8 邻域全判定 | 素材量×5 种地形=235 张，AI 产能不可承受 ✗ |
| 13 变体 blob | 13 | 4 邻域+对角 | ①对边情况（N+S 邻居）无专用 tile，只能复用单边 tile → 一侧出硬接缝；②对角相接有伪影；③查表逻辑绕 |
| 9-slice | 9 | 4 邻域 | 凹角/两向混合缺失，只适合矩形规则区域 |
| **16 变体直接映射** | **16** | **4 邻域 bitmask 直接当索引** | 对角相接（仅对角邻居）有轻微硬角——玩家自画路径的常见形状下不明显，可接受 |

**结论：有机轮廓地形（水/耕地/石板/木板/室内地板）用 16 变体直接映射；矩形规则区域可降配 9-slice（数据表加 `blend:'9'|'16'|'none'` 字段）；草地/泥地用单 tile。** 总 tile 数约 88-110 张，是 47 方案的 1/2.5，且**索引=bitmask，零查表逻辑**：

```
bitmask = (有N邻居?1:0) | (E?2:0) | (S?4:0) | (W?8:0)
tileIndex = bitmask            // 不需要任何查找表
绘制规则：bit=0 的方向画混合边（草地渗入），bit=1 的方向无缝
```

16 组合与语义（供美术出图对照，一图一格）：

| idx | 邻居 | 语义 | | idx | 邻居 | 语义 |
|---|---|---|---|---|---|---|
| 0 | 无 | 孤岛（四边混合） | | 8 | W | 东+南+北混合 |
| 1 | N | 南+东+西混合 | | 9 | N+W | 东+南混合 |
| 2 | E | 西+南+北混合 | | 10 | E+W | 南北向水道（上下混合） |
| 3 | N+E | 西南混合 | | 11 | N+E+W | 南混合 |
| 4 | S | 北+东+西混合 | | 12 | S+W | 北+东混合 |
| 5 | N+S | 东西向水道（左右混合） | | 13 | N+S+W | 东混合 |
| 6 | E+S | 西北混合 | | 14 | E+S+W | 北混合 |
| 7 | N+E+S | 西混合 | | 15 | 全 | 中心满铺（水=动画帧） |

> 产线提示：AI 生成整张 16-sheet 时给"逐格对照表"提示词（§18 提示词表模式），QA 用合成检查脚本把 16 格自动拼一个十字+转角样图目检；若 AI 一致性不过，退级方案=手绘 4 边+4 角+中心共 9 张，离线脚本合成 16 变体（像素混合边按 tile 手绘才无接缝，脚本只做裁切摆放）。

## 3. 河流

### 3.1 河岸变体规则

- **河岸不是独立 terrainId**，而是 WATER 的 16 变体渲染结果：bit=0 的边画"草渗入水面"的岸线。直/弯/宽全部自然涌现：
  - **直河段**：两岸各一列 idx=5（N+S 通道）或 idx=10（E+W 通道）；
  - **弯道**：外侧 idx 3/6/9/12（凸角），内侧 idx 13/14/11/7（凹边），凸角天然圆弧、凹角天然收口；
  - **宽河**：中间行/列全是 idx=15 中心水；宽度≥3 时中央可放 1-2 个波纹装饰变体。
- 岸线装饰（芦苇/石块/泡沫点）是**装饰层随机点缀**（按格子 hash 决定是否放置，不进存档——由种子派生，§7.1），放在 WATER 的 bit=0 边邻接格上。
- MVP 河流形状固定（基线地图预置，存档迁移时自动获得，§7.3）；"挖池塘/填河"列为二期开放项（§10 Q2）。

### 3.2 流动动画：**帧动画**（否决 UV 动画）

| 维度 | 3 帧帧动画（推荐） | UV 滚动 shader |
|---|---|---|
| 实现 | 水中心 tile 3 帧 500ms 轮换，仅 ~150-300 个水面 Sprite 换 spriteFrame | 水面独立层+滚动材质+与地面混合的 mask/边缘处理 |
| 微信容器风险 | 无（纯 2D batching，同一 atlas 同一材质 → 1 个 draw call） | 自定义 shader 编译与低端机 fillrate 风险；mask 叠层多一次 draw |
| 美术成本 | 3 帧×1 tile（可选+4 直边帧）=3-7 张 | 流动贴图 1 张但需手工调 wrap |
| 视觉 | 像素风标准做法，波纹循环感足够 | 连续流动感更好，但与像素点采样/整数镜头易出采样抖动 |

- 具体实现：`WaterLayer` 只为水面格子建 Sprite（不在镜头+1 屏裕量外的池化回收）；一个 500ms 定时器把层内所有 Sprite 的 spriteFrame 在 `water_sheet idx16/17/18` 间轮换（直边可选加入）。换帧操作 = 每格一次属性赋值，200 格/次在低端机 <1ms。
- 岸线（16 变体的混合边）**保持静态**，只有中心水动——既省美术又避免岸边抖动。
- **真机验收点**：WeChat 容器下 300 Sprite 换帧不掉帧、无闪白（换帧时避免整层重建，只改 spriteFrame 引用）。

### 3.3 桥的放置规则

- 工具=造桥锤；目标格必须 `terrain==WATER` 且**存在一组对侧邻居（N+S 或 E+W）为可走岸格**（GRASS/DIRT/TILLED/PATH/DECK 且非悬崖边界）→ 桥方向自动取该对（两对都满足时取先命中者， ghost 预览显示方向）。
- **两岸高度必须相等**（≤1 层落差自动用台阶语义？不——MVP 桥只允许两岸同层，落差≠0 时 ghost 变红提示"两岸高度不同，先修台阶"）。
- 桥格 `heightLevel = 岸格高度`；`BRIDGE` 可走；桥上不可钓鱼（判定见 §3.4）。
- 拆除：铲子点桥 → 返还 50% 材料（向下取整），桥消失恢复 WATER。
- 造桥消耗见 §6.2。

### 3.4 水域判定与钓鱼点

- `isBlocked(cell) = terrain==WATER && terrain!=BRIDGE`（VOID 同理）。移动判定是纯网格数学，无物理引擎（工程惯例）。
- **钓鱼点不存档、运行时派生**：格 c 是合法钓点 ⟺ `c 可走 && c 非 BRIDGE && c 4 邻域中有 WATER`。玩家进入距水面 ≤2 格范围时，邻水边缘显示涟漪高亮圈（复用 §5.3 "可行走平面"可读性语言）；点击该水边缘格 = 抛竿。桥格排除（站桥上垂钓列为风味二期）。
- 现有 FishingSystem 接口不变，只是"钓点集合"从单点改为上述派生集合（传入 cell → 鱼池权重可按"河/塘"水域标签扩展，MVP 仍单一鱼池）。

## 4. 台阶与高度

### 4.1 高度层模型

- `heightLevel: 0..3`，每格一个整数，存进 cell 字节（§2.1）。0=河岸基准层；住宅庭院推荐只用 0-1，最多 0-2（3 层以上可读性崩，硬上限）。
- 高度差通过**台阶格（STAIRS）**连接；台阶格自身的高度=其所连接的**高层**，绘制为斜坡贴图。

### 4.2 通行规则（手工网格判定，无物理）

```
canStep(from, to):                      // from/to 为相邻格（4 邻域）
  1. target 不可走（VOID/裸 WATER）→ 拒绝
  2. Δh = |h(to) - h(from)| > 1        → 拒绝（2 层落差任何方式都不可跨）
  3. Δh == 0                           → 允许
  4. Δh == 1：from、to 至少一方是 STAIRS → 允许；否则拒绝（不能直接攀/跳崖）
```

- 台阶格方向无关（MVP 不做朝向锁）：任一方向只要 Δ≤1 且邻格是台阶即可上下——降低玩家理解成本，代价是视觉上台阶贴图用两方向变体近似（ns/ew 按其高层邻居方位选择）。
- 角色在台阶格移动时 y-sort 键随所在格插值，无需特殊处理（假高度模型没有坐标偏移，见 §4.3）。
- 河流格 h=0，桥格继承岸高 → 桥两端天然 Δh=0 可走。
- 防守兼容：防守波次怪走 `events/defense_waves.json` 预设路径（全在 h=0 主路），台阶格对怪=阻挡（怪不爬台阶）→ **玩家造高台天然形成"怪不可达的安全种植位"**，作为二期防守深度钩子记录（§10 Q6），MVP 不调参。

### 4.3 立面渲染与 y-sort 配合（假高度，零坐标偏移）

- 高低边界判定：格 c 满足 `h(c) > h(c南侧格)` → 在 c 的南边界画立面 Sprite（1 层落差=16px、2 层=24px，1+2 组合直接用 24px 素材加一条横线层）；E/W 向落差画窄侧立面（8px 竖条，可选，MVP 可省略，靠崖顶描边表达）。
- 立面 Sprite 进入 `WorldContainer` 参与 y-sort：
  - **sortY = 南边界线的世界 y + 2**（微小偏移）；
  - 站在崖顶的实体 footY ≤ 边界线 → 画在立面后面（脚尖被崖沿盖 1-2px，视觉=站在崖边，正确）；
  - 站在崖底的实体 footY > 边界线 → 画在立面前面（正确）。
- **不做** per-level 的画面纵向偏移（有的伪 3D 会把高层整体上移 N px）——保持平面直角网格，凡坐标一律网格原值，可读性规范（脚底阴影）不需要任何例外。
- 台阶格自身不生成立面；台阶两侧的落差边界正常生成（斜坡贴图自带过渡）。

### 4.4 多高度地形可读性规范（复用并扩展 §5.3）

1. 脚底椭圆软阴影（25-35% 透明）= 可行走真值，**任何高度都保留**；
2. 立面统一用岩石/夯土纹理，1 层=浅色+草沿、2 层=深色+崖顶 2px 暗描边；
3. 角色被立面/建筑遮挡（在其北侧）时遮挡淡出至 40-50%（复用探险遮挡规范，同一条淡出代码路径）；
4. 台阶贴图必须"一眼是坡"：斜坡纹理 + 上下端 2px 亮/暗边；
5. 不可跨越的落差在玩家靠近时脚底阴影不出现 + 一次红叉抖动反馈（沿用"够不着给否定反馈"）。

## 5. 地窖：方案对比与推荐

### 5.1 两方案

| 维度 | 方案 A：同场景地下区（heightLevel/远端区域） | 方案 B：入口物件 + 独立室内场景 |
|---|---|---|
| 切换体验 | 无加载，走过去就到 | 一次场景切换（复用现有 farm→adventure 切换链 + 入口过场吞加载，探险图已验证 ≤2s） |
| 光照/氛围 | 一个场景两种氛围（暗蓝 cellar vs 户外），需要分区域环境光 hack | 室内场景天然挂暗色 ambient + 暖光圈，零 hack |
| 系统耦合 | 高：把"假高度"语义又搅进来（地下层到底算 h=-1 还是独立区域标志？），立面/y-sort/钓鱼派生都要加分支 | 低：地窖就是又一个室内场景，与住宅室内、装扮系统同构 |
| 存档 | 一个 terrain 数组 | 依然一个 terrain 数组（入口在户外）+ `save.cellar` 室内段——结构更清晰 |
| 装修衔接 | 要把 furniture 预布置系统搬进"户外场景里的暗区" | **直接复用 furniture.json 预布置管线与建议书 §3.2 的室内装扮二期方案**（{id,footprint,rot,layer} 按场景存） |
| 扩展性 | 地下多层（B2/B3）要再加区域偏移 | 新增场景文件即可，复用 SceneMgr 可替换接口（建议书 §6"场景管理留可替换接口"的既定决策） |
| 风险 | 与 §5.3"平面+遮挡"心智冲突，调试面大 | 切场景加载抖动（已有入口过场方案兜底） |

### 5.2 推荐：**方案 B**（拍板建议）

理由按权重：①装修/家具管线零改造直接复用（装扮是已拍板的二期系统，地窖等于白得一个装修场景）；②不与刚砍掉的高度系统产生任何语义纠缠；③氛围/光照/音频免费获得；④符合"三区分离、场景切换 + 可替换接口"的既定架构决策。方案 A 唯一实质优势（无加载）已被入口过场模式覆盖。

**地窖规格（v1 固定布局）**：
- 入口：庭院内可放置的"地窖门"物件（1×1 格，木 trapdoor 贴图，热区 88px）；`interact → 过场（掀盖+黑屏 0.6s）→ cellar 场景`。
- 室内：22×14 格（704×448 px），石墙 + `INDOOR_FLOOR` 泥土地板，固定一部木梯回入口位；氛围=暗蓝 ambient 35% + 入口暖光圈（r=160px 递减）。
- 功能：6 个储物箱位（interact=storage，衔接背包）、3 个陈设架（展示作物/鱼标本，读图鉴数据）、酒桶/腌渍桶（二期料理）。
- 装修：v1 沿用 furniture.json 预布置（新增 `cellar_id` 家具行）；二期可编辑摆放按 §3.2 方案落地，布局存 `save.cellar.furniture`（按场景 key，与住宅室内并列）。
- **与地形改造的衔接（二期亮点）**：地窖室内复用同一 TerrainMap+渲染器，开启"挖掘扩建"=室内也变成可编辑地形（铲墙→扩房间，消耗石材）——编辑代码全复用，这是选 B 的隐藏红利。

### 6.1 工具选择 UI（数值）

  3. 铺装器（长按 400ms 弹出子选盘：石板路 / 木平台；子选盘 2 槽 × 88px 竖排）
  4. 造桥锤
  5. 台阶锹（在落差边界放置台阶格）

### 6.2 消耗表（衔接 EconomySystem）

现有 items.json 已有 `wood`（木材）；**需新增 `stone`（石材）行**（探险产出，sellPrice≈4，探索区"潮湿洞窟"掉落，衔接 §11 资源表）。EconomySystem 增加通用 `spendCost(costs: {itemId:string;count:number}[]): boolean`（全部够才扣，任一不足返回 false 并 emit 'itemSpent'{fail:true}——沿用"禁止静默失败"教训 #16/#29）。

| 操作 | terrain 变化 | 消耗/格 | 备注 |
|---|---|---|---|
| 锄头·开垦 | GRASS→TILLED | 免费 | 现有行为 |
| 铲子·还原 | TILLED/PATH/DECK/STAIRS→GRASS（或→DIRT 若原为泥地） | 免费，**返还 50% 建材**（向下取整） | 有作物/有 farm.plots 数据的 TILLED 拒绝并提示 |
| 铲子·拆桥 | BRIDGE→WATER | 免费，返还 50% 木材+金币 | |

| 铺装器·木板 | →WOOD_DECK | wood×1 | |

- 经济校验（对齐 §11.1 通胀控制）：以普通作物日收益（约 20-40 gold/天）为锚，铺满 100 格石板路 ≈ 3-5 天纯收益 → 地形改造是**中期金币蓄水池**，前期只够小修小补；建材把探险产出接进家园建设（"探险服务农场"支柱）。
- 价格全部进 `catalogs/terrain_ops.json` 数据表（TABLE_MANIFEST 增加一行），不硬编码——调价不改代码。

### 6.3 单格与拖刷

- 单格：点按即改（低于 150ms）。
- **拖刷**（复用农田"工具锁定+拖刷"手感）：按住移动超 24px 进入刷子模式，扫过的合法格连续变更（逐格触发 spendCost，**余额不足即停**并在状态条显示"材料不足"）；拖刷中 ghost 显示整条路径。
- 刷子尺寸 MVP=1×1（3×3 刷列为二期， farm 场景验证拖刷误触率 <5% 后再放大）。
- 一次拖刷产生**一条撤销记录**（不是每格一条）。
- 拖刷合法性与 §6.2 的每格前置校验一致：桥要求对岸对、台阶要求落差边界、铺装不可覆盖 TILLED(有种)/BRIDGE/STAIRS（需先铲）。

### 6.4 拆除与恢复

- 原则（对齐 §8.3"失败不清档、损失可恢复"）：**任何拆除免费且返还 50% 建材；玩家永远不会因"造错"而卡死**。
- 铲子的还原目标由"原始地形"决定：基线地图里预置的 DIRT 主路还原为 DIRT，其余还原为 GRASS；预置 WATER/主路结构（桥位除外的河道、固定农田框）**不可铲**（红叉反馈）。
- 撤销栈：会话内存，容量 20 条操作，跨天/切场景清空；不进存档（防止存档膨胀与操作重放复杂度）；状态条提供"撤销"按钮 + Toast"已撤销（返还材料）"。

## 7. 数据结构与存档

### 7.1 运行时结构（TerrainSystem.ts，新增 gameplay/terrain/）

```ts
export interface TerrainSave {
    w: number;            // 96
    h: number;            // 56
    /** RLE+base64：[u16 run][u8 ((terrain<<3)|height)]* 小端序 */
    cells: string;
    /** 地窖入口物件（1×1，y-sort Sprite） */
    cellars: { x: number; y: number }[];
    /** 户外可放置物（盆栽/路牌/长椅等，二期扩）；v1 可为空数组 */
    decor: { itemId: string; x: number; y: number }[];
}

export class TerrainMap {
    private cells: Uint8Array;                       // w*h
    getTerrain(x,y): number; getHeight(x,y): number;
    /** 唯一写入口：改数据→emit('terrainChanged',{cells:[i...]})→渲染器标脏对应分块 */
    setCell(x,y,terrain,height): void;
    isWalkable(x,y): boolean;      // §3.4/§4.2
    canStep(from,to): boolean;
    /** 装饰层派生：hash(x,y) 决定点缀，不进存档 */
    decorSeed(x,y): number;
}
```

- 装饰点缀（草花/岸芦苇/石子）由 `(x*73856093 ^ y*19349663) % N` 派生，**不存档**；只有玩家显式放置的 `decor` 进存档。

### 7.2 序列化：**RLE 全量存，不做增量**

- RLE：`[u16 run][u8 value]` 逐对，Uint8Array → 拼包 → base64 存 `cells` 字符串。
- 体积估算：96×56=5376 格；基线地图（河/路/农田框）约 250-400 个 run → 二进制 ~750-1200B → base64 ~1.0-1.6KB；玩家长期改造后 run 数上升 2-3 倍 → 稳态 **<5KB**。
- **为什么不用增量**：全量 RLE 本身就只有几 KB，增量 diff 栈却引入无限增长、压缩、冲突三类复杂度——负收益。存档体积远低于"超 700KB 再分片"红线（建议书 §4.4）。
- 落盘时机沿用现有规则（结束一天/防守结算/切场景/onHide 强制 flush），地形变更不打断编辑，仅在既有存档点捎带。

### 7.3 SaveData v3 迁移（SaveManager.ts 改动点）

```ts

    /** v3 新增：地窖室内（布局 v1 固定，预留家具数组） */

}
const migrations: Record<number, (d: AnyRecord) => AnyRecord> = {
    2: (d) => ({ ...d, codex: Array.isArray(d['codex']) ? d['codex'] : [] }),
    // v2→v3：老档没有 terrain → 发基线地图（DataTables 里读 home_baseline.json）

```

- 基线地图 = `assets/data/maps/home_baseline.json`（DataManager 的 TABLE_MANIFEST 增 `maps/home_baseline`；内容即 §7.2 的 RLE 串 + 分区标注），由离线工具从 Tiled 或手写生成器产出。

- 兼容红线复查：只加字段不删字段 ✓；纯数据（id/坐标/数值）✓；不序列化节点引用 ✓。

### 7.4 furniture.json 与地形的关系

| 层 | 数据 | 存储 | 说明 |
|---|---|---|---|
| 户外地形 | terrainId/height/桥/台阶 | `save.terrain.cells`（RLE） | 本文档系统 |
| 户外物件 | 地窖门/盆栽/路牌 | `save.terrain.cellars` + `decor[]` | 1×1 格吸附，y-sort |
| 住宅室内（预布置） | furniture.json 现有 10 行（px+decorPos） | **不动** | 展示间沿用；数据表后续按建议书 §3.2 升级 {id,footprint,rot,layer} 时在 v4 迁移 |
| 地窖室内 | 固定布局 + 预留 `save.cellar.furniture` | v3 建空段 | 复用同一套家具表（加 cellar 类目行） |

- **furniture.json 不进地形系统**：家具是"格上物件"，地形是"格本身"；两者只通过"家具占地格必须 walkable 且高度=0"这一条校验相连（室内无高度概念，天然满足）。
- 现有 `FarmSave.plots`（作物数据）保持独立数组不并入 terrain.cells：作物有生长状态机，格子只有地形语义；`TILLED` 地形格与 `plots[i]` 通过同一下标映射（家园地图上农田区固定 12×8=96 格，i = 区内线性序），farm 逻辑零改动。

## 8. Cocos Tilemap 评估与渲染实现

### 8.1 结论先行：**编辑型地形不选 CC Tilemap，选自研分块渲染器**

CC 3.8 TiledMap 的能力边界与社区证据：

- TiledMap 面向"编辑器产出的静态 TMX"；运行时逐格改 tile 的官方支持很弱——社区实测 3.x 动态改 TiledTile/动态换 tmxAsset 存在已知问题（[TiledTile 动态改 grid 不生效帖](https://forum.cocos.org/t/topic/141929/3)、[3.7.3/3.8 动态设置 tmxAsset 报错帖](https://forum.cocosengine.org/t/tiledmap-settiledgidat-not-work/59910/2) 评论提及 3.7/3.8 仍存在、[代码动态创建 TiledMap 帖](https://forum.cocosengine.org/t/create-tiledmap-from-code-dynamically-in-cc3/52804) 确认资产必须经编辑器导入，内存拼 TMX 不可靠）；
- 而**地形改造系统 100% 依赖运行时逐格写**（拖刷一次写几十格）——用 CC Tilemap 等于长期踩在未文档化行为上，且微信容器表现还要再乘一层不确定；
- 我们需要的绘制规模极小（5376 格、屏内 ~1150 格、90-110 个 tile 图样、3-4 层），自研渲染器 2-3 天可落地，且 y-sort、水面动画、ghost 预览全部可控。

CC Tilemap 保留的用途：**探险/防守等静态图可以用它**（无运行时编辑需求），团队可先在静态图上积累 Tilemap 经验，与家园地形互不绑定。

### 8.2 推荐架构：TerrainRenderer 分层渲染（全部走 UI_2D 层，pitfall #1 照办）

```
home 场景 Canvas
 ├─ GroundLayer     地面静态合成：每分块(chunk) 1 个节点 1 个 Sprite
 │    chunk=16×16 格=512×512px；96×56 → 6×4=24 个 chunk，屏内仅 ~6 个
 │    烘焙：启动/标脏时用离屏 canvas 把该 chunk 非水格逐格 drawImage(atlas)
 │          → Texture2D.uploadData（或 canvas 引用）→ 单 Sprite 显示
 │    编辑：setCell 只标脏所在 chunk → 重烘 1 个 chunk（256 次 drawImage + 1 次
 │          纹理上传，中端机 <5ms），拖刷多格合并到帧末一次性重烘
 ├─ WaterLayer      水面动态层：每个水格 1 个池化 Sprite（§3.2 帧动画）
 │    只保留镜头+1 屏裕量内的水面 Sprite（河道 ~200-300 个），同一 atlas
 │    自动合批 → 1 draw call；500ms 换帧只改 spriteFrame
 ├─ WorldContainer  y-sort 容器（自写 sortY 每帧排序，实体 ≤60+立面 ~100）
 │    玩家/宠物/NPC/立面/地窖门/户外物件/建筑立绘
 └─ OverlayLayer    交互反馈（ghost 预览、钓鱼涟漪圈、红叉），常驻最上
```

- 纹理内存：24 chunk × 512×512，若用 RGBA4444 ≈ 12MB——**改用按需策略**：只烘屏内及裕量 chunk（≤10 个常驻，≈2.5-5MB），出屏 chunk 释放；或 chunk 降为 16×16 RGBA4444。真机实测定档（§9 spike）。
- 备选简化版（若烘焙路线在微信容器遇阻）：屏内 tile Sprite 池化（~1150 节点，单 atlas 合批 1 draw call），代码最简、节点数偏多——作为 spike 的 A/B 备选。
- 镜头约束沿用拍板：整数像素纯平移 → 分块 Sprite 与网格完全对齐，无半像素采样缝（pitfall #20 nearest 采样配合）。

### 8.3 y-sort 与"Tilemap 只做地面"的遮挡方案（若未来任何静态图用了 CC Tilemap，同样适用）

- Tilemap（或 GroundLayer）永远是**最底层**，z 序固定，绝不参与 y-sort；
- 一切有"立面"语义的东西——台阶立面、建筑、树、家具外置物——都是 WorldContainer 里的独立 Sprite，按 sortY 排序；
- 排序键：`sortY = footWorldY`（立面=底边 y+2）；每帧排序实体+立面（≈160 个元素，插入排序增量维护成本可忽略）；
- 遮挡淡出：玩家 sortY 与遮挡物 sortY 交叉且水平重叠时，遮挡物 opacity 40-50%（复用探险图的遮挡淡出实现）。

### 8.4 微信容器风险清单（家园地形相关）

| # | 风险 | 缓解 |
|---|---|---|
| W1 | chunk 烘焙的 canvas→Texture 上传在低端机卡顿 | 编辑合并到帧末；首屏分帧烘焙（每帧 ≤2 chunk）；真机压测 |
| W2 | 纹理内存超限（iOS WebView 更苛刻） | RGBA4444 / 按需 chunk / chunk 尺寸降 8×8 |
| W3 | 水面 Sprite 数量失控（玩家后期满图挖塘时） | WaterLayer 硬上限 500 格，超出部分降级静态（不动画） |
| W4 | point 采样在整数镜头下仍可能出现 1px 缝 | atlas 相邻 tile 留 1px padding（extrude） |
| W5 | onHide 时烘焙中断 | flush 存档先行（既有规则），重建渲染在 onShow 全量重跑 |
| W6 | 首包体积 | tiles 图集 pngquant ≤300KB，进首包可承受（首包预算 ≤3MB，建议书 §8） |

### 8.5 若静态图采用 CC Tilemap 的要点备忘（供探险/防守图）

- 层划分：地面层（terrain+变体）/ 装饰层（点缀、泡沫，无碰撞语义）/ **遮挡与立面绝不进 Tilemap**（见 §8.3）；
- 动画 tile 用 Tiled 的 animation 支持，**先在微信容器真机验证**（社区对动态 tile 支持的负面报告集中在运行时修改，静态动画 tile 风险较低但未验证）；
- tmxAsset 运行时替换是已知雷区（W 系列同源），静态图避免一切运行时重设。

## 10. 风险与开放式问题

**风险**
1. **渲染路线真机不定论**（W1/W2）——T0 spike 是硬闸门，不过闸则降级 Sprite 池方案并锁 chunk 需求；
2. **AI 产线 16 变体一致性**——退级方案已备（9 素材离线合成，§2.3）；产线排期先行 1 个地形试点；
3. **多高度可读性**——§4.1 已把假高度定为红线，但"台阶能不能一眼看懂"仍是当年 spike 未回答的问题，T4 需做 5 人可见性测试；
4. **编辑与防守并存**——防守复用家园地图，玩家在预告期改地形可能破坏波次预设路径 → MVP 规则：**预告发布后至防守结算前锁定庭院编辑**（Toast 说明），二期再把"地形即布防"做成正式机制；
5. **撤销不进存档**——玩家跨天丢失撤销能力是可接受取舍，但需在状态条 tooltip 说明，避免"撤销键失灵"误判。

**开放式问题（需要拍板/原型回答）**
- Q1 河流 MVP 完全不可改（含填河）是否满足"调整地形"的期待？还是至少开放"填河造地"（高成本：stone×5/格）？
- Q2 挖池塘/改河道若二期开放，水位与动画帧如何派生（静态水位表 vs 邻接传播）？
- Q3 台阶方向无关（MVP 提案）vs 方向锁（更真实的坡道）——5 人测试后再定；
- Q4 户外家具（decor[]）要不要 MVP 就给 2-3 件（盆栽/路牌）撑庭院氛围？涉及室外 y-sort 物件管线的提前；
- Q5 地窖扩建（室内挖掘）与 §3.2 室内可编辑装扮二期并行，数据结构 `{id,footprint,rot}` 是否足以表达"挖出的房间"（可能需要 cellar 单独 terrain 段）；
- Q6 高台防守钩子（§4.2）是否在二期做成正式机制（远程怪视距/陷阱抛物线）；
- Q7 基线地图 home_baseline.json 的产出工具（Tiled 手绘导出 vs 代码生成器）——影响美术工作流，T1 前定。
